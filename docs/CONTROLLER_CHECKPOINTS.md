# Controller checkpoints for prediction (#120)

`VehicleController.captureState()` returns a detached version-1 controller
checkpoint; `restoreState()` restores it under the same approved vehicle
configuration and surface sampler. The drivetrain, nitro, drift, burnout,
suspension and backfire modules expose corresponding internal state methods.
These methods are not called from the fixed-step update path. No checkpoint
capture, network payload or additional allocation was added to normal driving.

## Captured state and ownership

The checkpoint includes smoothed steering/pedals, gearbox mode/RPM/shift cut,
nitro charge, ignition/surge, perfect-window and button/release history; drift
entry arms, braking/countersteer/exit timers and score; burnout latch/intensity;
per-wheel suspension/compression/peak, contact data and visual roll; and exhaust
burst timers, effects and deterministic random seed. Drafting, launch push and the
local drift-mode selection are also captured. Temporary scratch vectors and the
drift guide are overwritten before use and are not checkpoint history.

Capture copies arrays, nested objects and vectors. Restore copies their values
into existing objects without retaining checkpoint references. Intentional
`Infinity` timers (`Drift.sinceEnd`, `Backfire.sinceHigh/sincePop`) use `null` in
checkpoints and restore to `Infinity`, so a JSON round trip does not silently
change idle timer semantics. Other values are preserved without clamping, which
would alter deterministic replay. Version and wheel-count mismatches are rejected
before controller mutation.

These are **trusted internal checkpoints**, not an untrusted input format or
public network schema. Primitive restore methods assume complete state produced
by a matching capture. They do not validate arbitrary JSON, authenticate its
source, bind it to a manifest or guarantee atomic rollback for malformed input.
A future authoritative wire decoder must validate the entire bounded payload,
version, tick and approved config/fingerprint before calling these methods.
The backend must never restore controller state supplied by a racer.

A controller checkpoint does not contain the rigid body, Rapier solver/world,
track geometry, tick, input mailbox, race rules/checkpoints/laps or event-consumer
state. Restore those matching boundaries separately. Replaying must suppress
historical audio/score/reward announcements rather than emitting them twice.
This chunk does not enable client prediction or change any server-authored result.

## Evidence and limits

Tests JSON-round-trip checkpoints and replay future inputs through each pure
module, comparing subsequent outputs and all captured state. Controller fixtures
restore a complete Rapier world snapshot and rebind controllers to its original
body handles. Subsequent controller states and rigid-body motion match exactly
for one racer at several mid-drive checkpoints and for two ghost racers sharing a
world, using the same construction/update order. They also cover copied state and
version/wheel-count rejection without mutation.

These fixed-timestep, flat-ground fixtures use the default car configuration.
They do not prove determinism across browser/CPU/WASM versions or real network
corrections. Restoring full Rapier world bytes is a local proof technique, not a
proposal to stream the collision world in each network frame. A pose/velocity-only
restore is not proven equivalent to a full world restore.

The next prediction chunks must define bounded server-authored correction state,
server/input application tick semantics, a bounded local input journal and replay
budget, local predicted physics, correction smoothing and stale/out-of-order
recovery. Test measured latency/jitter/loss and full controller restoration before
claiming responsive reconciled driving. The approved simulation fingerprint is
regenerated by the usual build because controller source files changed. Existing
recorded benchmarks retain their older fingerprint and are not silently relabeled.
